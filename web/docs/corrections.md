## 2. Interchange format: sixteen points (data-model.md 5.1, 6 and 8)

Reported by the builder while implementing the reader, the merge and the writer. Decided as follows. Section 6 of data-model.md still has the earlier text, and section 9 has no vectors for these rules yet.

Two general rules:

- **G1, storage invariant.** Whatever is stored is in the form the reader produces, so the exporter's output passes the schema and R1 to R10 without repair. Every write path (interchange import, transcript import, capture, edits through the API or through sync) runs the same normalisation before storing. A second import of the app's own export reports every project and session as unchanged.
- **G2, open values.** `provider` and `role` are normalised by one function: trim; an empty result becomes the fallback (`other`, `unknown`); if the value equals a known value when only the ASCII letters A to Z are folded, the known lower-case value is stored; otherwise the trimmed value is stored as written. "Trim" here removes only U+0020, U+0009, U+000A, U+000B, U+000C and U+000D, and the fold is ASCII only, so that JavaScript, Swift and SQL give the same result. A CHECK constraint that states this in SQL uses `translate()` for the fold and `btrim(value, <that list>)` for the trim, never `lower()` or a bare `btrim()`.

```ts
const isOpenValueSpace = (c: number): boolean => c === 0x20 || (c >= 0x09 && c <= 0x0d);
function normalizeOpen(value: string, known: readonly string[], fallback: string): string {
  let start = 0;
  let end = value.length;
  while (start < end && isOpenValueSpace(value.charCodeAt(start))) start++;
  while (end > start && isOpenValueSpace(value.charCodeAt(end - 1))) end--;
  const v = value.slice(start, end);
  if (v === "") return fallback;
  const folded = v.replace(/[A-Z]/g, c => String.fromCharCode(c.charCodeAt(0) + 32));
  return known.includes(folded) ? folded : v;
}
```

The trim is a loop on purpose: an expression of the form `<class>+$` takes quadratic time on a long run of blanks that does not end the string (section 3, point 14), and a hostile value can be megabytes long. For the same reason `provider` and a message `role` are limited to 200 characters each, checked before any normalisation (data-model.md 7.10).

The points, by the builder's numbers:

1. **`parseTags` is idempotent** (8.2). The leading run of `#` and white space is removed: `part.trim().toLowerCase().replace(/^[#\s]+/, "").trim()`. Repair 4 of 6.6 is `tags = parseTags(tags.join(","))`, which also splits an element that contains a comma and drops duplicates across elements. For tags, "trimmed" means what JavaScript's `trim()` removes (U+0009 to U+000D, U+0020, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFF; the same set as `\s`), and "lower-case" is `toLowerCase()`.
2. **R3 and repair 8** (6.6). Repair 8 stands. R3 is the writer's rule; a reader checks it after repair 8 and counts the destination vault's projects of the same user as present.
3. **Order of repairs** (6.6). Repair 5 (string cleaning) runs first, then the others in the order listed. The numbers stay.
4. **Repair 6** (6.6) sorts and renumbers only when every message of the session has a finite number as `index` (ties by array position; a fraction or a negative number sorts and is mended). Otherwise nothing in that session is renumbered and validation refuses the document.
5. **Repair 1** (6.6) also lower-cases `sha256` values, in attachment descriptors and in attachment segments. Entry names inside a ZIP bundle stay strict (6.4).
6. **Repairs 2 and 3** (6.6). `null` is read as absent for every optional property that version 1 defines, `generator` and its fields and `data_base64` included; an unknown property with the value `null` is kept as written. Repair 2 is G2.
7. **Repair 9** (6.6). `data_base64` that is not a string, cannot be decoded, or does not match `byte_length` or `sha256` is removed with a warning; the descriptor stays. Writers emit standard base64 with padding. Readers accept padding as optional: only the characters `A-Z a-z 0-9 + /`, then at most two `=`; without the `=` the length is not 1 modulo 4; no white space; no URL-safe alphabet. Length and hash judge the bytes.
8. **Timestamps** (6.1, R1). Digits beyond the millisecond are cut, never rounded, and cut before the value reaches PostgreSQL (`timestamptz(3)` rounds). One repair line per document with a count. Hour 24 and second 60 are refused. The year is 0001 to 9999.
9. **Projects in a merge** (6.7, step 2). Same id: equal content is "unchanged"; a later `updated_at` replaces the whole project (name, name key, `created_at`, `updated_at`, unknown properties); an equal or earlier `updated_at` with different content is "kept" and reported, as for sessions. If the incoming name's key already belongs to another project of the user, nothing of the project is changed and a warning is given.

With the keys of 7.2 (`PRIMARY KEY (owner_id, id)`) an id held by another user never collides: two users can hold the same ids, and nobody gets a fresh id because of another user.

Ignored: `updated_at`, the presence of `data_base64`, message ids, the order of properties. The incoming session is compared after the project ids of step 2 were mapped (point 18).

The order of properties inside an object carries no meaning: tests compare parsed values, never bytes, except the context packs of 9.3. The order of attachments is not decided yet; keep the order of the imported array until it is.
13. **A message's `model`** (6.8). `""` or `null` is read as absent; a writer never writes an empty one.

One function: wherever code decides which known provider a string stands for, it uses G2's `normalizeOpen`, not `trim().toLowerCase()`: the label in `contextPackMarkdown` (8.3 then reads `PROVIDER_LABEL.get(normalizeOpen(session.provider, KNOWN_PROVIDERS, "other")) ?? 15. **Signatures** (8.3, 8.5) take `readonly` arrays.
16. **File names** (5.1, B15). One function, the steps in this order: (1) replace `\ / : * ? " < > |`, the control characters U+0000 to U+001F and U+007F to U+009F, the bidirectional controls U+061C, U+200E, U+200F, U+202A to U+202E and U+2066 to U+2069, and lone surrogates by `-`; (2) trim white space at both ends and the trailing run of dots and white space, where white space is what `trim()` removes; (3) cut to at most 120 UTF-8 bytes without splitting a code point, and trim the trailing run of dots and white space again; (4) an empty result becomes `session`; (5) if the name begins with a dot, or if the part before the first dot, without trailing U+0020, is a device name in any letter case (A to Z), put `_` in front and apply step 3 again. The device names, from Microsoft's page "Naming Files, Paths, and Namespaces" as read on 2026-11-20: `CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, and `COM` and `LPT` followed by U+00B9, U+00B2 or U+00B3. The page does not list `COM0` and `LPT0`; the function treats them as device names too, as a precaution. The rule about U+0020 before the dot (`CON .txt` counts) is a precaution as well: the page says only that a name "followed immediately by an extension" is equivalent. Properties to test: the result is never longer than 120 bytes; it holds none of the replaced characters; it is not empty; it does not begin with a dot; its part before the first dot, without trailing U+0020, is no device name; and the function applied to its own result changes nothing. The bidirectional controls and the leading dot were added on 2026-11-20 after the review of the first screens: a title comes from a page or a file, such a control can make a name show another ending than it has, and most file managers hide a name that begins with a dot. A consequence of the order: a tab or a line break at an end of a title becomes `-` and stays, while a space is trimmed. design.md 5.4 takes this function in place of the `safeFileName` it prints; its three cases do not change. (Decided 2026-11-20; the order and the properties were checked on 4.1 million generated names.)
17. **`normalize("NFC")`** (8.1, 8.4). Both sections print it. On a run of combining marks that are not in canonical order (marks of different classes that have to be reordered) it takes time that grows with the square of the run, in V8 and in JavaScriptCore: for "a" followed by 80,000 marks, U+0323 and U+0301 alternating, 2.2 to 3.3 s in Node 25 and 7.6 to 12.5 s in the JavaScriptCore shell on the same Mac on 2026-11-20 (the builder measured 1.6 s in V8 on its own machine). A run of one class, or of several classes already in order, takes time that grows with the length. The product composes with a function of its own that gives the same string in time that grows with the length; a test compares the two on generated text, including long runs, Hangul and marks that have to be reordered. Where a limit of 7.10 applies (a project name: 200 characters) it is checked before the name is composed; the pure module has no such limit, and a summary or a search query is protected by the function alone.
18. **Projects on import** (6.7, step 2). Step 2 runs in two passes over the projects of the file, each in id order (the order of the file carries no meaning). Pass 1: every project whose id exists for this owner (a). Pass 1 is repeated until a round changes no project, because a rename that was refused (the name belonged to another project) can succeed after that project was renamed by the same file; it ends after at most one round more than the file has such projects, and each project is reported once, with the outcome it ended with. Pass 2: the others (b, then c). Then the result does not depend on the order of the file, and importing the same file again changes nothing. Example: the vault holds a project named X; the file holds that project renamed to Y and a new project named X. One pass in file order can merge the new project into the stored one by name before the rename frees the name; the two passes give two projects at once. Two cases stay as they are: two projects of one file with the same name key (R11) become one project, the one with the lower id; and two renames that exchange two names are never applied (each is refused because of the other, with the warning, on every import). Not covered by any order inside one file: two files imported one after the other, where a merge by name in the first and a rename in the second can still leave a session in the other project. (Decided 2026-11-20; checked on 8.6 million small cases and 3 million random ones.)
19. **`extra`** (7.2, 7.6; sync.md 6.1). `extra`, as a write path hands it to the normalisation of G1 and as a device sends it in `session.create`, is a plain JSON object or absent. `null` counts as absent, and absent is stored as `{}`. Anything else is refused: an array, a string, a number, a boolean, and an object that is not a plain object (a `Date`, a `Map`, an instance of a class). The pure constructor refuses the whole draft; a route that receives `extra` from a client checks it first and answers `validation` (sync.md 6.5), never an internal error. Known property names inside `extra` are dropped (6.8). In an interchange file `extra` has no special meaning: a property of that name, also with the value `null`, is an unknown property like any other and is kept under that name (6.5). (Decided 2026-11-20.)

Also decided: a property NAME that contains U+0000 or a lone surrogate cannot be stored in PostgreSQL `jsonb`; the cleaning pass drops such a property, with a warning.

## 3. Importer: seventeen points (import-rules.md, the reference port, design.md, capture.md)

Reported by the builder while implementing the transcript importer. The 57 fixtures that existed when these points were decided, and their expected files, do not change; fixtures 58 to 61 came later, with W6. Points 16 and 17 are entries 1.5.1 and 1.4.1 above. Points 18 to 22 were added on 2026-11-20, after the points before them had been implemented and reviewed.

Rules (import-rules.md):

1. **W2, UTF-16** is decoded leniently: decode the bytes in pairs; an odd last byte is ignored; an unpaired surrogate becomes U+FFFD. (Wording settled between the two sessions on 2026-11-20. `TextDecoder` alone does not do this: for an odd last byte it appends U+FFFD, measured on Node 24 and 25, and the reference port, which uses it, differs from the rule there until it is corrected in its web mode.) The rule against a non-fatal decoder is about UTF-8, where a failure is what tells UTF-8 from windows-1252.
2. **W2, UTF-16 without a mark** needs at least two byte pairs before the zero-byte test applies.
3. **W2, a UTF-8 mark followed by invalid UTF-8** falls through to the rows below with all its bytes. The user then sees the windows-1252 flag, and the three mark bytes as characters at the start, in the review step.
4. **W1 is idempotent.** Step 1 removes the leading run of U+FEFF and U+0000: every U+FEFF at the start, also one that stands behind a U+0000. (Wording settled between the two sessions on 2026-11-20: "every leading U+FEFF" alone is not idempotent, because the later step that removes U+0000 can uncover another U+FEFF.) Every entry point applies W1, and `parseText` applies it again; twice changes nothing.
5. **W4, `create_time`** gives a date only when it is a finite number whose instant lies in the years 0001 to 9999. For the order of nodes the number is used whenever it is finite. A `create_time` that is not a finite number counts as absent: 0 for the order (it ties with a node that has no time, in key order), and no date. `JSON.parse` reads `1e999` as `Infinity` and `-1e999` as `-Infinity`. (Measured on the Apple side on 2026-11-20, for import-rules.md 2.5.1 under "Observed": a positive number too large for a double, such as `1e999`, `1e400`, `1e309` or `1.8e308`, anywhere in the file, also in a member the importer does not read, makes the reader refuse the whole file, which is then imported as raw text (D9); `-1e999` and `-1e309` are read as negative infinity, and such a node sorts before every other; `1e308` is read and sorts last; a conversation `create_time` of 253402300800 gives a date in the year 10000, and one of `1e308` or `-1e999` is accepted and gives the session a date outside any calendar. So the web differs from the Apple app here on purpose: it counts `-1e999` as 0, and such a node then sorts after one with a negative time.)
6. **W10, a capture title** is never blank and never holds U+0000. Every candidate goes through W1 and the full trim; the first that is not empty wins: typed name, detected title, the last non-empty path segment of the link (percent-decoded; if decoding fails, as written), the link itself, and last the constant `Captured session`.
7. **W1 applies to every stored string**, also the title passed by the caller, the source link and the file-name stem.
8. **"Empty" means empty after the full trim** wherever a W rule tests a title or a message for emptiness. A message of only U+000B, U+000C, U+0085, U+2028 or U+2029 is no message, and such a title falls back. What is stored for a message that is not empty does not change, except what W6 says about text on a header line.
9. **W8, marker words** are matched with ASCII case folding only. The claim about the Apple app becomes "identical for ASCII text". This is about the marker words only. Measured on 2026-11-20: the Apple app takes no line whose marker is spelled with U+0130 for a marker (`A` + U+0130 + `: two`, `ASS` + U+0130 + `STANT:` and two more), so ASCII folding gives its result there. The guard phrases of 2.6 keep `toLowerCase()`. Measured the same day over every Unicode scalar value, in Node, JavaScriptCore and Swift: outside the ASCII letters only U+0130 (to `i` + U+0307) and U+212A (to `k`) have a lower case that holds an ASCII letter, and `toLowerCase()` and Swift's `lowercased()` give the same text for both. The answers of the guards still differ where 2.3 says, because Swift compares whole characters. One such case comes from the lower-casing itself: `MEET GEMIN` + U+0130 counts as `meet gemini` on the web and not in the Apple app, since the lower case of U+0130 ends in a combining mark. With U+212A the two agree: `COO` + U+212A + `IE` is `cookie` in both. For 2.3, the row on `hasPrefix`, `==` and `contains`: a marker or a phrase that is immediately followed by a combining mark, U+200D or a variation selector, or immediately preceded by a prepend character such as U+0600, is not found by Swift and is found by JavaScript.
10. **`importFile` has a fourth outcome, `interchange`,** that carries the parsed document for a file whose `format` is `sessionvault-interchange`; the caller hands it to the interchange reader. It is never reported as `unrecognised_json`. `decodeBytes` returns the text as decoded, before W1.

Added on 2026-11-20:

18. **W10, a restored turn that gives no message** stays left out. In `importCapture` for `kind` "turns": a restored turn that gives no message (nothing is left after the cleaner and the full trim, or only a label, W12) is not restored. It goes back into `dropped_turns`, in input order, with its `position` and with the text it has there without `keep_dropped`: the input turn after W1, which for a turn dropped from the front still has its header lines. Its label does not count for the provider. The result is the one the call gives without that index; so when every turn is dropped and no named turn gives a message, the result is `rejected`, `no_conversation_found`, with every turn in `dropped_turns`. `stripChromeTurns(turns, keep_dropped)` itself does not change: it returns the restored turn among the kept ones, and its sentence "`dropped` then holds only the turns that stay dropped" stays. The paragraph after the code block of W10 becomes: "A restored turn is then treated like any kept turn (cleaner, full trim, leading marker); one that gives no message stays in `dropped_turns`." One more line for the worked example: the three turns of fixture 41 with the last one replaced by `Claude can make mistakes. Please double-check responses.`; `keep_dropped` [2] gives the messages user, assistant and `dropped_turns`: trailing 2. The reference port gets the same change. No fixture and no line of the worked example changes (run with the change made in a copy of the port).
19. **W6, a turn whose only text stands on its header line** is stored as that text, fully trimmed: `You said: x` followed by U+2028 is stored as `x`. The cleaner cannot remove such a turn: if it leaves nothing, the header-line text, fully trimmed, is the message. W6 says "the label text as written" there, which keeps a character that only the full trim removes: `You said: 10:42` followed by U+2028 has to be stored as `10:42`. In W6, "header-line text" names the text after the header, and "label" stays the word for speaker labels. No fixture changes (run in a copy of the port: all 61 and 59 equal).

Known defects of the reference port (`../reference/import-port/importer.ts`), not fixed yet:

11. Time-order ties follow `Object.keys`, so mapping keys that look like integers come first; W4 asks for the order of the keys in the JSON text.
12. Role lines of a context pack are looked up in a plain object, so a line that is the name of something every object inherits (`constructor`, `toString`, `__proto__`) after `---` is taken for a role line. Look roles up in a `Map`.
13. Two patterns use `.`, which does not match U+2028 or U+2029, so a fence line or an Origin line that contains one is not recognised, although lines are cut at LF only (2.3).
14. The trim expressions are quadratic on a long run of blanks inside a line (one line of 160,000 spaces took 10.6 s in the builder's measurement), and the Origin pattern on repeated " (". On a server this is a way to stall the process with one hostile page or file: trim with loops, not with expressions of the form `<class>+$`.
15. It is not written for a strict compiler, and its W1 skips the lone-surrogate step on a platform without `String.prototype.toWellFormed`.

Found on 2026-11-20:

20. Its web mode sorts by a `create_time` that is not finite (`1e999` last, `-1e999` first) and prints a date outside the years 0001 to 9999 (`+010000-01-01T00:00:00.000Z` for 253402300800). Point 5 says 0 for the order and no date.
21. Its web mode matches marker words with `toLowerCase()`, so `A` + U+0130 + `:` is taken for a marker. Point 9 says ASCII folding.
22. Its apple mode differs from the Swift importer where no fixture goes: it does not refuse a file that holds a positive number too large for a double; and for a conversation `create_time` outside 1582-10-15 to 9999-12-31 its text differs from the harness, which prints Julian dates before 1582-10-15 and the year 10000 without a sign, and which says so when a date cannot be printed (not finite, or further from 1970 than 8.64e12 seconds).

Do not adopt the port as product code without fixing these. The product importer has a test for each, among them one line of 1,000,000 blanks that must be parsed within a second.
